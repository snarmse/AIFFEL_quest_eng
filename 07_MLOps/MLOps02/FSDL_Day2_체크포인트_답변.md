## Chapter 7. 현대적 ML 엔지니어를 위한 개발 환경

### 1. VS Code의 원격 개발 기능이 필요한 이유

ML 학습에 필요한 대규모 데이터와 GPU는 보통 원격 서버에 있습니다. VS Code Remote를 사용하면 소스 분석, 코드 실행, 디버깅은 GPU 서버에서 수행하고 화면만 로컬 PC에 표시할 수 있습니다. 따라서 데이터를 로컬로 계속 옮길 필요 없이 원격 GPU와 파일을 사용하면서도 로컬 에디터처럼 편리하게 개발할 수 있습니다.

### 2. 주피터 노트북의 문제와 하이브리드 해결책

- **실행 순서 문제:** 셀을 순서대로 실행하지 않으면 과거 상태가 남아 결과가 달라질 수 있습니다. 핵심 로직을 순차 실행되는 `.py` 모듈로 옮기고 노트북에서는 이를 불러와 사용합니다.
- **리팩토링 문제:** 노트북에서는 함수 이름 변경이나 코드 이동이 어렵습니다. 모델, 데이터 로딩, 학습 코드를 `.py` 파일로 분리하면 VS Code의 Rename Symbol, 타입 검사, 린팅을 사용할 수 있습니다.
- **버전 관리 문제:** `.ipynb`에는 출력과 이미지까지 들어가 Git diff가 복잡하고 단위 테스트도 어렵습니다. 핵심 코드를 텍스트 기반 `.py` 파일로 관리해 Git diff와 테스트를 쉽게 만듭니다.

노트북은 탐색과 시각화에 사용하고 핵심 코드는 모듈로 관리합니다. `%autoreload 2`를 사용하면 모듈을 수정한 뒤 노트북을 재시작하지 않아도 변경 사항이 반영됩니다.

### 3. 결정적 빌드가 보장되지 않을 때의 문제

예를 들어 한 사람이 `pip install torch transformers`로 환경을 만들고 일주일 뒤 팀원이 같은 명령을 실행하면, 그사이 라이브러리 버전이 바뀌어 서로 다른 환경이 만들어질 수 있습니다. 그 결과 한쪽에서는 코드가 실행되지만 다른 쪽에서는 호환성 오류가 나거나, 같은 코드와 데이터로도 학습 결과가 달라질 수 있습니다. Python·CUDA 버전과 모든 패키지 버전을 잠그고 환경 설치 절차를 자동화해야 이런 문제를 막을 수 있습니다.

### 4. `requirements.in`과 `requirements.txt`의 차이

`requirements.in`에는 프로젝트가 직접 사용하는 `torch`, `transformers` 같은 패키지와 최소한의 제약을 적습니다. `requirements.txt`에는 `pip-tools` 또는 `uv lock`이 계산한 하위 의존성까지 포함해 정확한 버전을 고정합니다. 즉, `.in`은 사람이 관리하는 요구사항이고 `.txt`는 동일한 환경을 재현하기 위한 잠금 결과입니다.

## Chapter 8. PyTorch 생태계 심화

### 1. Lightning 전환 후 직접 작성하지 않아도 되는 코드 5가지

1. 입력과 모델을 `.to("cuda")`로 직접 GPU에 옮기는 코드
2. 에포크와 배치를 순회하는 전체 학습 루프
3. `optimizer.zero_grad()`, `loss.backward()`, `optimizer.step()` 호출
4. 검증 시 `model.eval()`, `torch.no_grad()`를 설정하고 메트릭을 직접 합산하는 코드
5. 분산 학습, 혼합 정밀도, 체크포인팅, 로깅 등을 직접 구현하는 엔지니어링 코드

모델, 손실 함수, 최적화처럼 학습 내용은 `LightningModule`에 두고 GPU 관리와 학습 실행 방식은 `Trainer`에 맡깁니다.

### 2. `setup`과 `train_dataloader`의 역할 차이

`setup`은 원본 데이터를 읽고 변환을 적용한 뒤 train/validation/test 데이터셋으로 분할합니다. `train_dataloader`는 이미 준비된 `train_dataset`을 배치 크기, 셔플, `num_workers`, `pin_memory` 등의 설정과 함께 `DataLoader`로 감쌉니다.

두 작업을 분리하면 동일한 데이터 분할을 여러 모델에서 재사용할 수 있고, 데이터셋 구성과 로딩 성능 설정을 독립적으로 변경할 수 있습니다. 분산 학습에서도 Lightning이 각 단계와 GPU에 맞게 데이터 준비를 관리하기 쉬워집니다.

### 3. `_shared_step` 패턴 적용

분류 프로젝트의 공통 로직은 배치에서 `x, y`를 꺼내고, 모델로 logits를 계산하고, 손실과 정확도를 구하는 부분입니다. 이를 `_shared_step`에 둡니다.

- `training_step`: 공통 결과 중 `train_loss`, `train_acc`를 기록하고 역전파에 사용할 loss를 반환합니다.
- `validation_step`: `val_loss`, `val_acc`를 에포크 단위로 기록하고 진행 표시줄에 보여 줍니다.
- `test_step`: 최종 평가를 위한 `test_loss`, `test_acc`를 기록합니다.

공통 계산은 한 곳에 유지하면서 단계별로 메트릭 이름과 기록 방식만 다르게 합니다.

### 4. `overfit_batches=1` 실패 시 원인과 디버깅

1. **그래디언트가 끊겨 가중치가 업데이트되지 않음:** 학습 전후 파라미터가 변하는지 확인하고, 각 파라미터의 `grad`가 `None`인지 또는 0인지 검사합니다. `detach()`, `torch.no_grad()`가 학습 경로에 잘못 들어갔는지도 확인합니다.
2. **데이터와 레이블의 순서가 뒤섞임:** 한 배치를 직접 출력·시각화해 입력과 정답의 짝을 확인하고, 전처리와 셔플 과정에서 입력과 레이블에 같은 인덱스가 적용되는지 검사합니다.
3. **수치적 불안정성으로 NaN 발생:** loss, logits, gradient에 `NaN`이나 무한대가 있는지 단계별로 확인합니다. 우선 혼합 정밀도를 끄고 학습률을 낮추며, 필요하면 gradient clipping을 적용합니다.

### 5. 실제 프로젝트에 맞게 바꿀 부분

- `LitClassifier.__init__`: 실제 입력 크기, 은닉층 크기, 클래스 수에 맞게 모델 구조를 바꾸고 프로젝트에 맞는 사전 학습 모델, 손실 함수, 학습률을 설정합니다.
- `MyDataModule.setup`: 예제의 무작위 텐서 생성을 제거하고 실제 이미지와 레이블을 불러옵니다. 필요한 전처리·정규화를 적용하고 train/validation/test를 겹치지 않게 분할합니다.

## Chapter 9. GPU 하드웨어와 클라우드 인프라

### 1. 분산 학습에서 가장 중요한 지표

분산 학습에서는 **인터커넥트**가 특히 중요합니다. 각 GPU가 계산한 그래디언트를 계속 교환해야 하므로 GPU 자체의 연산이 빨라도 GPU 사이의 통신이 느리면 전체 학습이 기다리게 됩니다. 여러 차선의 고속도로가 있어도 톨게이트가 좁으면 정체되는 것처럼, GPU가 여러 대여도 PCIe 통신이 병목이면 성능이 GPU 수에 비례해 늘지 않습니다. NVLink는 GPU끼리 직접 고속 통신하게 해 이 병목을 줄입니다.

### 2. 시간당 비용보다 실험당 비용이 중요한 이유

노트북의 표에서는 레거시 GPU 4대를 이용한 AWS 실험이 시간당 약 24달러이고 72시간 걸려 약 1,750달러가 듭니다. 반면 최신 GPU 8대를 이용한 실험은 시간당 약 31달러로 더 비싸지만 8시간 만에 끝나 총비용은 약 250달러입니다. 시간당 가격만 보면 전자가 싸지만, 실험당 비용은 후자가 약 7분의 1이며 엔지니어의 대기 시간도 크게 줄어듭니다.

### 3. 스팟 인스턴스 사용의 전제 조건

스팟 인스턴스는 언제든 회수될 수 있으므로 자동 체크포인팅과 학습 재개 기능이 반드시 필요합니다. 체크포인트에는 모델 가중치뿐 아니라 옵티마이저 상태, 에포크 번호, 스케줄러 상태가 저장되어야 합니다. 체크포인트는 인스턴스가 사라져도 남는 저장소에 보관해야 하며, 마지막 체크포인트에서 자동으로 재개할 수 있어야 합니다.

### 4. W&B를 사용했을 때 편리한 점

학습률, 배치 크기, 모델 구조, 에포크 같은 설정과 train/validation loss 및 accuracy를 실험별로 자동 기록할 수 있습니다. 여러 실험의 곡선을 한 화면에서 비교해 어떤 설정이 좋은 결과를 냈는지 확인할 수 있고, GPU 사용률과 메모리 사용량도 함께 수집할 수 있습니다. 따라서 노트북이나 메모에 결과를 수동으로 기록하다가 최적 설정을 잃어버리는 문제를 줄일 수 있습니다.

## Chapter 10. 데이터 저장과 관리

### 1. 저장 지연 시간과 `num_workers`의 관계

저장 장치가 느릴수록 GPU가 다음 배치를 기다리는 시간이 늘어납니다. `num_workers`를 늘리면 여러 프로세스가 다음 배치를 미리 읽어 메모리에 올리므로 GPU의 대기 시간을 줄일 수 있습니다. 다만 네트워크나 S3에서 매번 직접 읽는 방식은 지연 시간이 너무 커서 worker 수만 늘리는 데 한계가 있으므로, 데이터를 GPU 가까이의 로컬 NVMe SSD로 옮기는 것이 우선입니다. 최적의 worker 수는 보통 CPU 코어 수의 절반에서 전체 사이에서 실험적으로 찾습니다.

### 2. 이진 데이터는 S3에, URL만 DB에 저장하는 이유

이미지, 오디오, 비디오 같은 큰 이진 파일은 확장성이 높은 객체 저장소에 적합합니다. DB에는 파일 위치를 가리키는 URL과 메타데이터만 저장하면 구조화된 검색과 갱신 성능을 유지할 수 있습니다. 이진 데이터를 DB에 직접 넣으면 DB 크기가 급격히 커지고 읽기·쓰기 성능이 떨어지며 백업과 복제가 어려워집니다.

### 3. OLTP와 OLAP의 차이

- **OLTP:** 행 지향 저장 방식으로 개별 레코드의 빠른 조회·삽입·수정에 적합합니다. 예를 들어 “사용자 A의 모든 주문을 조회하라”는 쿼리에 알맞으며 Postgres와 SQLite가 대표적입니다.
- **OLAP:** 열 지향 저장 방식으로 대량 데이터의 특정 열만 읽어 집계·분석하는 데 적합합니다. 예를 들어 “지난 30일 전체 이미지의 평균 해상도를 계산하라”는 쿼리에 알맞습니다. 필요한 열만 읽으므로 분석 속도와 압축률이 높습니다.

## Chapter 11. 데이터 레이블링과 품질 관리

### 1. 레이블링을 최소화하는 네 가지 전략

- **자기주도 학습:** 데이터 자체의 구조를 이용해 다음 토큰 예측이나 마스킹 복원처럼 별도 수동 레이블 없이 표현을 학습합니다.
- **데이터 증강:** 정답의 의미는 유지한 채 밝기, 회전, 크롭 등의 변형으로 한 원본에서 여러 학습 샘플을 만듭니다.
- **합성 데이터:** 알고리즘이나 생성 모델로 정답을 알고 있는 데이터를 직접 만들어 레이블링 비용을 줄입니다.
- **사용자 피드백:** 클릭, 스킵, 수정, 평점, 좋아요 같은 실제 사용 행동을 암묵적 레이블로 사용합니다.

이미지 분류 프로젝트에는 밝기·대비·크롭·회전 등의 **데이터 증강**을 먼저 적용할 수 있습니다. 서비스가 배포된 뒤에는 사용자의 정답 수정이나 평가를 수집해 새 레이블로 사용하는 방법도 적용할 수 있습니다.

### 2. 골드 표준 데이터셋이 필요한 이유

골드 표준은 엔지니어가 동일한 기준으로 직접 레이블링한 200~500개 정도의 기준 데이터입니다. 외주 레이블러의 결과를 이 기준과 비교해 정확도와 작업 품질을 평가할 수 있습니다. 골드 표준 없이 외주를 맡기면 레이블러마다 모호한 사례를 다르게 해석해도 이를 객관적으로 판별할 기준이 없고, 일관성 없는 데이터가 대량 생산될 수 있습니다.

### 3. 약지도 학습의 유지보수상 장점

수동 레이블링은 레이블 체계가 “긍정/부정”에서 “긍정/중립/부정”으로 바뀌면 기존 데이터를 사람이 다시 레이블링해야 합니다. 약지도 학습은 휴리스틱을 구현한 레이블링 함수를 수정한 뒤 전체 데이터에 다시 실행하면 수백만 개의 레이블도 빠르게 갱신할 수 있습니다. 즉, 레이블을 사람의 일회성 작업이 아니라 수정·재실행 가능한 코드로 관리한다는 점이 가장 큰 장점입니다.

### 4. LLM 합성 데이터가 효과적인 상황과 주의점

고객 문의와 친절한 답변처럼 텍스트 예시를 대량으로 만들거나, 실제 데이터가 부족한 희귀 사례와 다양한 표현을 보강할 때 효과적입니다. 생성 시 원하는 정답 형식을 함께 만들 수 있어 초기 레이블링 비용도 줄어듭니다. 그러나 LLM의 편향, 사실 오류, 중복, 부자연스러운 패턴이 학습 데이터에 들어갈 수 있으므로 합성 데이터의 품질을 반드시 검증하고 실제 데이터 및 골드 표준과 비교해야 합니다.

## Chapter 12. 데이터 버전 관리와 워크플로우 자동화

### 1. 현재 레벨과 한 단계 올리는 방법

노트북 실습처럼 데이터가 로컬 폴더에 있고 어떤 시점의 데이터로 학습했는지 별도로 기록하지 않았다면 현재 상태는 **Level 0(무관리)**입니다. Level 1로 올리려면 학습할 때 사용한 데이터 전체를 날짜나 버전별 폴더에 스냅샷으로 저장하고, 각 모델이 어떤 스냅샷으로 학습됐는지 기록해야 합니다. 이후에는 이진 데이터를 S3에 두고 URL과 레이블을 담은 Parquet/JSON 장부를 Git LFS로 관리하는 Level 2로 발전시키는 것이 실용적입니다.

### 2. 데이터 버전 관리 없이 모델을 롤백할 때의 문제

지난주 배포한 모델은 정상인데 이번 주 새 데이터로 재학습한 뒤 성능이 떨어졌다고 가정하겠습니다. 코드만 지난주 커밋으로 되돌려도 데이터 폴더가 이미 이번 주 데이터로 덮어써졌다면 지난주 모델을 다시 만들 수 없습니다. 코드가 같아도 데이터가 다르면 다른 모델이 나오기 때문입니다. 어떤 샘플과 레이블을 사용했는지 기록이 없으면 오류를 만든 데이터도 추적할 수 없습니다.

### 3. Level 2의 장부 비유

실제 이미지나 오디오 파일은 큰 창고인 S3에 그대로 두고, 각 파일의 주소와 레이블이 적힌 목록만 Git으로 관리하는 방식입니다. Git에서 지난주 목록으로 돌아가면 그때 사용한 파일들의 주소와 정답 구성이 그대로 복원됩니다. 무거운 원본을 매번 복사하지 않고도 정확한 데이터셋 버전을 다시 구성할 수 있습니다.

### 4. 워크플로우 자동화가 필요한 시점

프로젝트가 서비스 단계로 넘어가 데이터 추출, 특징 생성, 기존 모델 분석, 재학습 같은 작업을 매일 또는 매시간 반복해야 할 때 자동화가 필요합니다. 작업 간 선후관계가 있고 실패 시 재시도·중단·상태 모니터링이 필요하다면 Airflow 같은 DAG 도구가 적합합니다.

반대로 한 대의 PC에서 가끔 실행하며 단계가 적고 실패했을 때 사람이 다시 실행해도 되는 작업은 단순한 Python 또는 Unix 스크립트로 충분합니다. 데이터 규모와 의존성이 작을 때부터 전문 도구를 도입하면 운영 복잡성만 커질 수 있습니다.

## Day 2 통합 체크포인트

### 1. 환경 점검

단순히 노트북에서 그때그때 `pip install`을 수행했다면 결정적 빌드가 완전히 보장됐다고 보기 어렵습니다. 팀원에게 동일한 환경을 전달하려면 다음 자료가 필요합니다.

- Python과 CUDA 등 기반 환경을 정의하는 Conda 환경 파일 또는 `pyproject.toml`
- 직접 의존성을 적은 `requirements.in`
- 하위 의존성까지 정확히 고정한 `requirements.txt` 또는 lock 파일
- 설치 명령을 자동화한 `Makefile`
- 실행 방법과 필요한 환경 변수를 설명한 `README.md` 및 예시 환경 파일

이 파일들을 코드와 함께 Git에 커밋하고 `make install` 같은 한 명령으로 설치되게 하면 재현성이 높아집니다.

### 2. Lightning 리팩토링 계획

노트북 8.13의 분류기를 기준으로 다음과 같이 분리합니다.

- **`LightningModule`:** 모델 구조, `forward`, 손실 함수, 정확도 계산, 옵티마이저와 스케줄러를 담당합니다.
- **`training_step`:** 배치의 순전파와 loss·accuracy 계산, `train_loss`·`train_acc` 기록, 역전파에 사용할 loss 반환을 담당합니다.
- **`validation_step`:** 동일한 공통 계산 뒤 `val_loss`와 `val_acc`를 에포크 단위로 기록합니다.
- **`configure_optimizers`:** AdamW와 CosineAnnealingLR을 생성해 반환합니다.
- **`Trainer`:** GPU 수, DDP, 혼합 정밀도, 최대 에포크, gradient clipping, 체크포인팅, early stopping, W&B 로깅을 담당합니다.

### 3. 인프라 설계

8.13의 소규모 이미지 분류 예제라면 먼저 단일 GPU로 시작합니다. 로컬 GPU가 없다면 실험과 프로토타이핑 비용이 낮은 RunPod나 Lambda Labs 같은 GPU 전문 클라우드에서 24GB급 GPU를 사용합니다. 여러 GPU나 H100은 프로파일링 결과 단일 GPU가 병목이고 실험 속도를 크게 줄일 수 있을 때 선택합니다.

실험 관리는 W&B를 사용해 하이퍼파라미터, loss, accuracy, GPU 사용량을 기록합니다. 구체적인 GPU 단가가 노트북에 제시되어 있지 않으므로 예상 비용은 `시간당 GPU 가격 × 실제 학습 시간`으로 산정합니다. 예를 들어 시간당 1달러인 GPU로 한 실험이 2시간이면 실험당 2달러이며, 10회 실험은 약 20달러입니다. 이는 계획용 가정이며 실제 단가와 프로파일링 결과로 갱신해야 합니다.

### 4. 데이터 전략

공개 이미지 데이터셋이나 직접 수집한 이미지로 시작하고, 먼저 엔지니어가 100개 이상을 직접 레이블링해 모호한 사례를 확인합니다. 이후 레이블링 가이드라인과 200~500개의 골드 표준을 만듭니다. 밝기·대비·크롭·회전 같은 증강으로 레이블 수를 늘리지 않고 데이터 다양성을 확보하며, 초기 모델이 가장 불확실해하는 샘플만 추가 레이블링하는 능동적 학습도 적용합니다.

데이터 버전 관리는 최소 Level 1로 시작한 뒤, 원본 이미지는 S3에 두고 URL과 레이블을 담은 Parquet/JSON 파일을 Git LFS로 관리하는 Level 2로 전환합니다.

### 5. 비용 시뮬레이션과 스팟 조건

초기 소규모 분류 실험을 단일 GPU에서 2시간, 총 10회 수행한다고 가정하면 총 GPU 시간은 20시간입니다.

| 선택지 | 시간당 비용(가정) | 실험 시간 | 실험당 비용 | 10회 비용 |
|---|---:|---:|---:|---:|
| 보급형 GPU | $1 | 2시간 | $2 | $20 |
| 고성능 GPU | $3 | 0.5시간 | $1.5 | $15 |

이 예시에서는 고성능 GPU가 시간당 세 배 비싸도 학습을 네 배 빠르게 끝내 실험당 비용이 더 낮습니다. 따라서 실제 선택 전 짧은 벤치마크로 학습 시간을 측정해야 합니다.

스팟 인스턴스를 사용하려면 `ModelCheckpoint(save_last=True)`로 모델 가중치, 옵티마이저, 에포크, 스케줄러 상태를 주기적으로 저장하고, 체크포인트를 영구 저장소에 보관하며, 중단 후 자동 재개할 수 있어야 합니다. 이 조건을 갖추면 회수 위험을 감수하고 70~90% 할인된 자원을 사용할 수 있습니다.

## 최종 정리

Day 2의 핵심은 탐색용 노트북과 프로덕션 코드를 분리하고, Lightning으로 학습 코드를 구조화하며, GPU 비용을 실험당으로 계산하고, 코드와 함께 데이터도 버전 관리하는 것입니다. 작은 프로젝트에서는 단순한 도구로 시작하되 반복 작업과 의존성이 커질 때 체크포인팅, W&B, Level 2 데이터 관리, 워크플로우 자동화를 단계적으로 도입하는 것이 적절합니다.

# 06DP08 제출 — 투자 글 요약 서비스

## 1. 프로젝트 개요

사용자가 직접 붙여 넣은 한국어 투자 글을 Hugging Face의 `eenzeenee/t5-small-korean-summarization` 모델로 요약하는 서비스입니다. 입력한 글을 FastAPI 백엔드에서 검증·요약한 뒤 Streamlit 화면에 결과를 표시합니다.

> 결과는 원문의 핵심을 빠르게 파악하기 위한 참고 정보이며 투자 권유가 아닙니다. 숫자, 종목명, 전망은 반드시 원문과 대조해야 합니다.

### 구현 항목

- FastAPI `GET /health`, `POST /predict`
- Pydantic 입력·출력 검증
- `X-API-Key` 인증
- `run_in_executor`를 이용한 비동기 추론
- 예외 로깅과 401·422·500 HTTP 응답
- Swagger UI 및 Streamlit 프론트엔드
- 입력이 512 토큰을 넘을 때 잘림 여부 안내

## 2. 실행 및 확인 방법

1. `investment_summarizer_submission.ipynb`를 Colab에 업로드합니다.
2. 위에서 아래 순서로 셀을 실행합니다. 최초 모델 다운로드에는 시간이 걸릴 수 있습니다.
3. 서버 실행 셀의 Swagger UI에서 `GET /health`와 `POST /predict`를 확인합니다.
4. 요청 헤더에 `X-API-Key: test-key-001`을 넣고 20자 이상의 한국어 글을 전송합니다.
5. Streamlit 실행 셀에서 텍스트를 입력하고 요약 결과를 확인합니다.

자동 테스트 셀은 health check 200, 인증 누락 401, 잘못된 입력 422, 정상 추론 200을 차례로 검증합니다. 요청에 따라 실행 화면 캡처는 제출하지 않습니다.

## 3. 세션별 체크포인트 답변

### 세션 1 — 모델 선택과 단독 추론

**어떤 도메인과 태스크를 선택했는가?**  
투자 정보 도메인의 한국어 텍스트 요약 태스크를 선택했습니다. 길게 작성된 글의 핵심을 빠르게 파악하는 것이 목적입니다.

**왜 이 모델을 선택했는가?**  
`eenzeenee/t5-small-korean-summarization`은 한국어 요약용으로 공개된 T5 계열 모델이고, 약 95.6M 파라미터의 소형 모델이라 교육용 CPU/Colab 환경에서 시연하기에 상대적으로 부담이 작습니다. 단독 추론으로 실제 한국어 요약문 반환을 먼저 확인한 뒤 서버에 연결했습니다.

### 세션 2 — 스키마와 입력 검증

**입력과 출력은 어떻게 정의했는가?**  
입력은 `text`, `max_length`, `min_length`이고 출력은 성공 여부, 요약문, 모델 ID, 입력 글자 수, 512 토큰 초과 여부, 투자 유의 문구로 정의했습니다.

**어떤 잘못된 입력을 막는가?**  
빈 문자열과 공백뿐인 문자열, 20자 미만 또는 10,000자 초과 글, 범위를 벗어난 요약 길이, `min_length`가 `max_length` 이상인 요청을 422 응답으로 차단합니다.

### 세션 3 — 모델 서비스

**모델 로드와 추론을 어떻게 분리했는가?**  
`load_model()`은 `lru_cache`로 모델을 한 번만 적재합니다. `summarize_text()`는 전처리, 요약 생성, 빈 결과 검사, 토큰 잘림 판단을 담당하여 API 코드와 모델 로직을 분리했습니다.

**긴 입력은 어떻게 처리하는가?**  
토크나이저 기준 512 토큰을 넘는지 먼저 계산하고 추론 시 `truncation=True`를 적용합니다. 응답의 `truncated` 값과 Streamlit 경고로 사용자에게 뒷부분이 잘렸음을 알립니다.

### 세션 4 — FastAPI, 인증, 비동기 처리

**API Key 인증을 제거하면 어떤 위험이 있는가?**  
누구나 비용이 큰 모델 추론을 호출할 수 있어 자원 고갈, 응답 지연, 서비스 장애와 운영 비용 증가로 이어질 수 있습니다. 실제 배포에서는 키를 코드가 아닌 비밀 저장소에서 관리하고 요청 제한도 함께 적용해야 합니다.

**왜 `run_in_executor`를 사용하는가?**  
Transformers 추론은 동기식이며 시간이 오래 걸릴 수 있습니다. 이를 별도 스레드에서 실행해 FastAPI 이벤트 루프가 막히지 않고 health check나 다른 요청을 계속 처리하도록 했습니다.

**오류는 어떻게 처리하는가?**  
인증 실패는 401, Pydantic 검증 실패는 422, 추론 중 예상하지 못한 예외는 서버 로그에 원인을 남기고 사용자에게 내부 정보를 노출하지 않는 500 메시지로 반환합니다.

### 세션 5 — 프론트엔드와 테스트

**사용 흐름은 무엇인가?**  
사용자가 Streamlit에서 API URL, API Key, 텍스트와 요약 길이를 입력하면 프론트엔드가 `POST /predict`를 호출하고 요약문, 잘림 경고, 투자 유의 문구를 표시합니다.

**무엇을 테스트했는가?**  
서버 상태 정상 응답, API Key 누락 거부, 짧은 입력 검증 실패, 유효한 요청의 정상 요약을 자동 테스트 셀로 확인하도록 구성했습니다.

## 4. Day 8 최종 체크포인트

**Q1. 본인의 프로젝트에서 Pydantic 검증은 어떤 잘못된 입력을 막아줍니까?**  
빈 글, 공백뿐인 글, 20자 미만 또는 10,000자 초과 글, 허용 범위를 벗어난 요약 길이, 최소 길이가 최대 길이 이상인 요청을 막습니다.

**Q2. `Depends(verify_api_key)`를 제거하면 어떤 위험이 있습니까?**  
인증되지 않은 사용자가 모델을 무제한 호출하여 CPU·메모리와 비용을 소모하고 서비스 품질을 떨어뜨릴 수 있습니다.

**Q3. `run_in_executor`를 사용한 이유는 무엇입니까?**  
동기식 모델 추론을 별도 스레드에서 실행해 FastAPI 이벤트 루프가 멈추는 것을 방지하고 다른 요청에 응답하기 위해서입니다.

**Q4. Day 1~8 중 가장 많이 참고한 Day는 어디였습니까? 왜입니까?**  
Day 7을 가장 많이 참고했습니다. 텍스트 모델을 서비스 계층으로 분리하고 FastAPI 비동기 엔드포인트와 Streamlit까지 연결하는 구조가 이번 프로젝트와 가장 유사했습니다. API Key 인증은 Day 6을 함께 참고했습니다.

**Q5. 실제 배포에 추가로 무엇이 필요합니까?**  
Docker 패키징, 클라우드 인프라, HTTPS, 비밀 키 관리, 요청 제한, 모니터링과 중앙 로그, 자동 테스트·CI/CD, 모델 버전 관리가 필요합니다. 저작권·개인정보 검토와 투자 유의 문구도 운영 정책으로 관리해야 합니다.

## 5. 프로젝트 회고

Day 1~7의 내용을 완전히 보지 않고 처음부터 작성할 수 있었던 것은 모델 단독 추론과 기본 FastAPI 엔드포인트였습니다. 반면 Pydantic의 필드 간 검증, API Key 의존성, 노트북에서 서버와 Streamlit을 백그라운드로 실행하는 부분은 교안을 다시 확인했습니다.

가장 어려웠던 점은 요약 결과의 토큰 길이를 적절하게 설정하는 일이었습니다. Streamlit UI에서 설정하는 최대 256 토큰은 **출력 요약문의 길이 제한**이고, 모델의 512 토큰은 **입력 글의 처리 한도**인데 처음에는 두 기준을 혼동하기 쉬웠습니다. 또한 최소 요약 토큰을 너무 낮게 설정했을 때 핵심 내용이 충분히 담기지 않은 매우 짧은 요약문이 생성되었습니다. 이를 개선하기 위해 UI의 최소 요약 길이 기본값을 40 토큰으로 높이고 최대 길이 기본값을 160 토큰으로 조정했습니다. 이 과정을 통해 입력 한도와 출력 길이를 구분하고, 사용자가 결과 길이를 조절할 수 있도록 설계하는 것이 중요하다는 점을 배웠습니다.

다시 만든다면 첫째, 긴 글을 문단 단위로 나누어 각각 요약한 뒤 최종 요약하는 계층형 요약을 적용하겠습니다. 둘째, 실제 투자 문서로 요약 품질과 숫자·고유명사 보존율을 평가하는 테스트 세트를 만들겠습니다. 셋째, API Key를 환경 변수와 비밀 저장소로 관리하고 요청 제한, 캐시, 관측성 도구를 추가하겠습니다. 마지막으로 모델 다운로드와 서버 준비 상태를 분리하여 readiness endpoint를 제공하고 Docker와 CI/CD로 재현 가능한 배포를 구성하겠습니다.

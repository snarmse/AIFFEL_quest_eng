## Chapter 0. 모델 배포, Full Stack DL, MLOps

### 1. 세 과정의 담당 범위와 분리 이유

- **모델 배포(FastAPI/Streamlit)**는 완성된 모델을 API나 화면으로 감싸 사용자가 접근할 수 있게 하는 서빙 인터페이스를 담당한다.
- **Full Stack Deep Learning**은 문제 정의, 데이터 신뢰성, 실험 재현성, 사용자 피드백, 성능 저하 추적 등 모델의 전체 생애주기와 ML 제품 설계를 담당한다.
- **MLOps**는 Docker, 클라우드, Airflow, CI/CD 등을 이용해 배포·재학습·모니터링을 안정적으로 자동화하는 인프라를 담당한다.

세 과정은 관심사의 깊이가 다르기 때문에 분리된다. 배포 기술만 알아서는 올바른 문제와 데이터인지 판단할 수 없고, 제품과 생애주기를 설계하지 않은 상태에서 MLOps 인프라부터 구축하면 잘못된 프로젝트를 효율적으로 자동화하게 될 수 있다.

### 2. 평평한 지구 ML, 둥근 지구 ML, 데이터 플라이휠

평평한 지구 ML은 데이터 수집→학습→평가→배포가 한 번 진행되고 좋은 성능이 나오면 끝났다고 보는 선형 관점이다. 둥근 지구 ML은 배포 이후 실제 사용자 데이터와 피드백을 다시 수집해 모델을 개선하는 순환 관점이다. 데이터 플라이휠은 이 외부 순환 루프의 엔진으로, 사용 증가→데이터 증가→모델 개선→제품 가치와 사용자 증가의 선순환을 만든다.

### 3. ML Powered Product와 MLOps의 지향점

- ML Powered Product의 질문: **“약사가 예측 결과를 어떻게 검토·수정하게 하고, 그 피드백을 다음 학습 데이터로 어떻게 만들 것인가?”**
- MLOps의 질문: **“새 판매 데이터를 이용한 재학습·검증·배포를 어떻게 안정적으로 자동화할 것인가?”**

전자는 사용자 가치와 상호작용을, 후자는 안정적인 운영 인프라와 자동화를 중심에 둔다.

## Chapter 1. ML 제품의 가치와 현대 ML 생태계

### 1. Software 1.0과 Software 2.0

Software 1.0에서는 개발자가 입력과 출력의 관계를 if-else 같은 명시적 규칙으로 작성한다. Software 2.0에서는 개발자가 데이터와 목적 함수를 정의하고, 최적화 알고리즘이 데이터에서 관계를 학습한다. 따라서 Software 2.0은 코드 테스트만으로 충분하지 않다. 데이터의 품질·분포·버전, 모델 평가, 실제 환경의 드리프트, 재학습과 모니터링까지 함께 관리해야 한다.

### 2. CACE가 ML 시스템에서 치명적인 이유

전통 소프트웨어는 컴포넌트 경계와 명시적 규칙이 비교적 분명해 변경 영향을 독립적으로 테스트하기 쉽다. 반면 ML에서는 학습 데이터, 특성, 파라미터 하나의 변경도 전체 예측 분포를 바꿀 수 있다. 예를 들어 휴일 정보의 정의를 바꾸면 여러 의약품의 수요 예측이 동시에 달라질 수 있다. 코드 diff만으로 원인을 설명하기 어렵기 때문에 데이터·모델 버전 관리, 회귀 평가, 롤백이 필수다.

### 3. 기술 범용화가 ML 엔지니어 역할에 미친 변화

Hugging Face, Foundation Model API, 성숙한 오픈소스 모델 덕분에 모델 자체를 처음부터 만드는 비용은 낮아졌다. 이에 따라 ML 엔지니어의 역할은 모델 학습·최적화에만 머무르지 않고, 적절한 모델/API 선택, 제품 통합, 평가, 데이터 플라이휠, 비용·보안·지연시간의 균형, 필요 시 파인튜닝까지 전체 시스템을 설계하는 방향으로 확장되었다.

## Chapter 2. ML 도입 여부와 우선순위

### 1. 실현 가능성 × 임팩트 매트릭스

약국 의약품 수요 예측 프로젝트는 초기에는 **실현 가능성 높음 × 임팩트 높음** 후보로 배치한다. 판매·입고·재고·달력 데이터가 이미 존재하고 시계열 예측이라는 유사 사례가 많아 기술적으로 접근 가능하다. 품절과 과잉 재고를 줄이면 환자 대기, 폐기, 자금 점유를 줄일 수 있어 비즈니스 임팩트도 크다. 다만 실제 데이터 품질과 개선 폭은 PoC로 검증해야 하므로 확정 판단은 아니다.

### 2. “API로 충분한가?”를 판단할 확인 사항

다음을 확인해야 한다.

1. API가 실제 약국 데이터에서 필요한 예측 성능을 내는가
2. 호출 비용이 자체 개발·운영 비용보다 합리적인가
3. 허용 지연시간과 가용성 요구를 만족하는가
4. 처방·판매 관련 민감 데이터를 외부로 보낼 때 보안·개인정보 조건을 충족하는가
5. 약국별 계절성이나 품목 특성에 맞게 커스터마이징할 수 있는가
6. 공급자 종속, 데이터 반출, 장애 시 대체 수단이 허용 가능한가

현재 프로젝트는 범용 LLM API보다 전통 시계열/회귀 베이스라인이 더 직접적이므로, API 도입 자체를 목표로 삼지 않는다.

### 3. ML 전에 시도할 네 가지 대안

1. **규칙 기반**: 최근 4주 평균과 안전재고 기준으로 발주량을 계산한다. 데이터가 적고 계절성이 단순할 때 적합하다.
2. **Human-in-the-loop**: 시스템은 후보 발주량만 제안하고 약사가 최종 결정한다. 오판 시 품절·과잉재고 비용이 크고 도메인 판단이 필요할 때 적합하다.
3. **Foundation Model API**: 자유 형식 문의 요약이나 문서 분류처럼 범용 NLP가 핵심일 때 적합하다. 수요 예측의 주된 대안은 아니다.
4. **전통적 통계 기법**: 이동평균, 회귀, 시계열 분해로 추세와 계절성을 예측한다. 해석 가능성과 적은 데이터가 중요할 때 강한 베이스라인이 된다.

## Chapter 3. ML 프로젝트 라이프사이클

### 1. 네 단계와 핵심 활동

1. **기획 및 설정**: ML 도입 여부, 예산, 성공 지표, 윤리적 조건을 정의한다.
2. **데이터 수집 및 레이블링**: 필요한 데이터를 모으고 정제하며 정답과 품질 관리 체계를 만든다.
3. **모델 학습 및 디버깅**: 단순 베이스라인부터 구축하고 실험을 비교하며 오류 원인을 찾는다.
4. **배포 및 모니터링**: 파일럿·회귀 테스트 후 배포하고 실제 성능과 사용자 피드백을 수집한다.

이 네 단계는 선형 완료가 아니라 문제 발견에 따라 앞 단계로 돌아가는 반복 구조다.

### 2. 4단계에서 2단계로 가장 자주 돌아가는 이유와 예방 질문

오프라인 학습 데이터와 실제 사용자 환경의 데이터 분포가 달라 배포 후 성능이 급감하기 때문이다. 학습에 없던 입력과 실패 사례를 실제 환경에서 모아 다시 레이블링해야 한다. 기획 단계에서는 “학습 데이터가 실제 운영 환경과 계절·품목·사용자 구성을 대표하는가?”, “배포 후 실패 사례와 정답을 어떻게 수집할 것인가?”, “드리프트를 어떤 지표로 감지할 것인가?”를 물어야 한다.

### 3. 자연적 플라이휠과 설계가 필요한 플라이휠

추천 서비스는 클릭·스킵·시청 시간이 사용 과정에서 자연스럽게 암묵적 레이블이 되므로 플라이휠이 비교적 자연스럽다. 반면 의약품 수요 예측은 판매량만으로는 품절 때문에 발생하지 못한 수요나 약사의 판단 이유를 알 수 없다. 따라서 예측값, 약사의 수정값, 실제 발주량, 품절 여부, 폐기량을 함께 기록하는 UI와 데이터 구조를 의도적으로 설계해야 한다.

## Chapter 4. ML 제품의 세 가지 아키타입

### 1. 아키타입별 실제 서비스

- **Software 2.0**: 넷플릭스·유튜브의 개인화 추천
- **Human-in-the-loop**: AI가 의심 영역을 표시하고 의사가 최종 판독하는 방사선 영상 판독 보조
- **Autonomous**: Waymo의 무인 자율주행

### 2. Human-in-the-loop에서 Autonomous로의 진화

초기에는 모든 발주 추천을 약사가 검토하고 수정한다. 충분한 운영 데이터가 쌓이면 신뢰도가 높고 실패 비용이 낮은 일반 품목만 자동 발주하고, 신뢰도가 낮거나 고가·필수 의약품은 계속 검토 대상으로 남긴다. 전환 조건은 실제 환경에서의 안정된 성능, 품목별 신뢰도 보정, 오류 비용 한도 충족, 드리프트 감지, 자동 처리 실패 시 되돌릴 수 있는 안전장치와 책임 범위의 합의다.

### 3. 만들 제품의 아키타입과 그 영향

이 프로젝트는 **Human-in-the-loop**로 시작한다. 의약품 품절과 과잉 재고의 비용이 있으므로 완전 자동화보다 약사의 최종 판단을 유지한다. 이에 따라 전체 품목에서 극단적으로 높은 정확도를 요구하기보다, 예측 구간과 신뢰도를 제시하고 위험 품목은 사람이 검토하게 한다. 약사의 수락·수정, 실제 판매·품절·폐기 결과를 피드백으로 저장해 플라이휠을 만든다.

## Chapter 5. 팀과 조직 설계

### 1. 필요한 다섯 역할과 풀스택 ML 엔지니어의 범위

필요한 역할은 ① ML 엔지니어/Applied Scientist, ② 데이터 엔지니어, ③ ML Platform 엔지니어, ④ 프로덕트 매니저, ⑤ 도메인 전문가다. 풀스택 ML 엔지니어는 소규모 PoC에서 모델 선택·학습, 데이터 파이프라인 일부, API·데모 배포, 기본 실험 관리까지 넓게 맡을 수 있다. 그러나 사용자 가치의 우선순위와 약학적 타당성까지 혼자 대체할 수는 없으며, 규모가 커지면 데이터와 플랫폼 업무도 전문화할 필요가 있다.

### 2. 리서치와 프로덕션의 거리를 좁히는 일하는 방식

모델 개발자가 노트북 결과만 넘기는 방식에서 벗어나 직접 FastAPI/Streamlit 데모를 만들고 실제 입력으로 검증해야 한다. 연구·데이터·제품·운영 담당자가 같은 성공 지표와 평가 데이터를 사용하고, 작은 변경을 빠르게 파일럿으로 확인해야 한다. 재현 가능한 실험 기록과 데이터 버전을 공유하며, 배포 중 발견된 오류가 즉시 데이터 수집과 다음 실험으로 연결되도록 공동 책임을 가져야 한다.

## Chapter 6. 실전 기획 체크리스트

### 1. 가장 답하기 어려운 세 질문

1. **성공 지표**: 예측 오차 감소가 실제 품절률·폐기율·재고 회전율 개선으로 얼마나 이어지는지 사전에 확정하기 어렵다. ML 메트릭과 비즈니스 메트릭을 함께 정의해야 한다.
2. **라벨**: 실제 판매량은 품절이 없었다면 팔렸을 잠재 수요와 다를 수 있다. 정답 데이터를 어떻게 보정할지가 어렵다.
3. **실패 비용**: 과소 예측은 품절과 환자 불편을, 과대 예측은 과잉재고와 폐기를 만든다. 품목별 가격·필수성·유효기간이 달라 하나의 비용으로 환산하기 어렵다.

### 2. 네 가지 멘탈 모델의 약국 도메인 적용

- **예측 비용 하락**: 약사가 수백 품목의 발주량을 매일 개별 판단하는 시간을 자동 예측으로 줄인다.
- **마찰 감소**: 재고·판매 추세·휴일을 여러 화면에서 확인하는 과정을 한 번의 추천과 예외 검토로 줄인다.
- **Software 2.0**: 품목마다 누적된 복잡한 안전재고 if-else 규칙을 데이터에서 학습한 예측으로 보완한다.
- **업계 벤치마킹**: 유통·리테일의 수요예측과 재고 최적화 사례에서 품절률, 폐기율, 재고 회전율 개선 방식을 참고하되 약국의 규제와 필수 의약품 특성에 맞춘다.

### 3. 정확도와 비용의 비선형 증가, 요구 정확도를 낮추는 설계

99%를 99.9%로 높이기 위해 더 많은 데이터, 정교한 레이블, 실험, 컴퓨팅, 검증이 필요해 비용이 크게 늘 수 있다. 이 프로젝트에서는 모든 품목의 완전 자동 발주를 목표로 하지 않는다. 예측 구간과 신뢰도를 표시하고, 낮은 신뢰도·고가·필수 품목만 약사가 검토하며, 추천량을 사람이 수정할 수 있게 한다. 또한 상위 수요 품목부터 적용하고 안전재고 규칙을 병행하면 모델에 요구되는 정확도를 낮출 수 있다.

### 4. 지금 필요한 도구와 나중에 필요한 도구

**지금 필요한 것**은 샘플 데이터, 주피터 노트북, 단순한 통계/ML 베이스라인, 기본 실험 기록, Streamlit 데모, 수동 주간 평가다. **나중에 필요한 것**은 Docker 기반 환경 격리, Airflow 재학습 파이프라인, 클라우드/Vertex AI, 모델 레지스트리, 실시간 A/B 테스트, 대규모 Feature Store다. 먼저 2~4주 PoC로 비즈니스 임팩트와 핵심 가정을 증명하고, 반복 작업이 실제 병목이 될 때 자동화를 도입한다.

## Day 1 통합 체크포인트

### 1. 세 단계 학습 경로에서 Day 1의 위치

모델 배포를 배우면 모델을 사용자에게 전달할 수 있지만, 그것이 올바른 문제를 풀며 지속적으로 개선되는 제품인지는 알 수 없다. Day 1은 배포 직후 문제 정의, ML 도입 판단, 아키타입, 비용, 팀, 데이터 플라이휠과 기술적 부채를 검토하게 한다. 이 설계가 있어야 다음 MLOps 단계에서 무엇을 어떤 수준으로 자동화할지 결정할 수 있다. 따라서 Full Stack DL은 “서빙할 수 있음”과 “안정적으로 자동 운영함” 사이에서 올바른 ML 제품과 생애주기를 설계하는 단계다.

### 2. 종합 기획

1. **ML이 정말 필요한가?** 이동평균·안전재고 규칙을 먼저 베이스라인으로 만들고, ML이 품절·폐기 지표를 유의미하게 개선하는지 검증한다.
2. **Build/Buy/API**: 범용 API보다 내부 판매 데이터에 맞는 전통 시계열/회귀 모델을 직접 구축하는 소규모 Build가 적절하다. 단, 처음부터 복잡한 딥러닝 모델을 만들지는 않는다.
3. **아키타입**: 약사가 최종 발주량을 승인하는 Human-in-the-loop다.
4. **실현 가능성 × 임팩트**: 데이터가 존재하고 검증된 예측 기법이 있어 실현 가능성은 높으며, 품절·폐기·업무시간을 줄일 수 있어 임팩트도 높다고 가정한다. PoC로 이 가정을 확인한다.
5. **비용의 3대 동인**: 판매·품절·재고 데이터의 가용성과 품질, 품목별 요구 정확도, 계절성·프로모션·공급 중단을 반영하는 문제 난이도다.
6. **PoC 종료 조건**: 2~4주 내 샘플 품목에서 규칙/통계 베이스라인 대비 유의미한 개선이 있고, 데이터 품질이 본 개발을 지지하며, 허용 비용·응답시간 안에서 동작해야 한다. 하나라도 충족하지 않으면 재정의하거나 중단한다.

### 3. 둥근 지구형 데이터 플라이휠

시스템이 발주 추천량과 신뢰도를 제시하면 약사는 이를 수락하거나 수정한다. 이 행동과 실제 발주량, 이후 판매량, 품절, 반품·폐기 결과를 저장한다. 특히 수정값과 수정 사유는 도메인 피드백 레이블이 된다. 새 데이터를 정기적으로 평가·재학습에 반영하면 품목별 예측과 신뢰도 분기가 개선된다. 더 정확한 추천은 약사의 검토 시간을 줄이고 품절·폐기를 낮춰 사용률을 높이며, 사용이 늘수록 다시 더 많은 피드백 데이터가 쌓인다.

### 4. 가장 가능성 높은 실패와 예방

가장 가능성 높은 원인은 **작은 문제 해결**이다. 예측 오차는 줄었지만 실제 발주 결정이 바뀌지 않거나 품절·폐기 감소가 작으면 복잡성만 늘어난다. 이를 막기 위해 기획 단계에서 예측 정확도뿐 아니라 품절률, 폐기율, 재고 회전율, 검토 시간 같은 비즈니스 지표와 최소 개선 기준을 정한다. 기존 규칙 기반 베이스라인과 비교하고, 2~4주 PoC 후 실제 약사 파일럿으로 의사결정 변화와 가치를 확인한다.

### 5. 배포 6개월 후 예상 기술적 부채

- **CACE**: 품목 분류, 휴일 특성, 결측치 처리 변경이 전체 예측에 예상 밖 영향을 줄 수 있다.
- **데이터 드리프트**: 계절, 감염병 유행, 처방 패턴, 고객 구성 변화로 수요 분포가 달라질 수 있다.
- **외부 세계의 불안정성**: 공급 중단, 도매 재고, 가격·급여·규제 변경이 과거 데이터로 설명되지 않는 변화를 만든다.

가장 큰 위협은 **외부 세계의 불안정성과 그로 인한 데이터 드리프트**다. 의약품 수요와 공급은 모델 밖 사건의 영향을 크게 받기 때문이다. 품목별 오차·입력 분포·품절률을 지속적으로 모니터링하고, 약사의 수정 사유와 공급 이슈를 수집하며, 성능 저하 시 수동 운영으로 되돌아갈 수 있어야 한다. 데이터·특성·모델 버전과 회귀 평가도 함께 관리해야 한다.
